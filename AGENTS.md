# Web safe-area insets: one source of truth, deliberately enforced

`react-native-safe-area-context`'s `useSafeAreaInsets()` hook (and `insets.top`/`insets.bottom` anywhere derived from it, and `<SafeAreaView>`) always reports `{top: 0, right: 0, bottom: 0, left: 0}` on web — but **this is NOT automatic**, and two earlier rounds shipped believing it was. The library's own web implementation is not inert: it appends a hidden probe `<div>` to `document.body` sized by `env(safe-area-inset-*)`, measures it, and feeds the real pixel values through `useSafeAreaInsets()`/`<SafeAreaView>` live. In ordinary desktop or mobile BROWSER testing there is no notch, so that measurement is 0 either way — indistinguishable from "does nothing." On a real installed standalone iPhone PWA it measures the REAL inset and applies it, which was quietly double-counting on top of this app's own fills (`AppTopBar`'s `<SafeAreaView edges={['top']}>`, the tab bar's `Math.max(insets.bottom, 6)`/`useTabBarHeight`, `DocThreadView`'s and `DocsGroupChatScreen`'s composer padding) — the actual cause of a "roughly double" top offset and a bottom dead zone that a standalone-simulation Playwright suite can't catch, because forcing this app's own CSS rules never touches the library's own independently-created probe element.

**The fix, and the rule going forward:** `App.tsx` renders `AppSafeAreaProvider` (see `src/components/AppSafeAreaProvider.tsx`), not the library's own `SafeAreaProvider`, on web — it pins `SafeAreaInsetsContext`/`SafeAreaFrameContext` to zero permanently, bypassing the library's web measurement entirely. This is what makes `useSafeAreaInsets()`/`<SafeAreaView>` actually, reliably report zero on web — by construction, not by accident of the test environment. Do not remove or bypass `AppSafeAreaProvider`, and do not add a new `<SafeAreaProvider>` anywhere else in the tree.

The ONE sanctioned reader of `env(safe-area-inset-top)` / `env(safe-area-inset-bottom)` on web is the hidden probe pair in `public/index.html` (`#safe-area-probe-top` / `#safe-area-probe-bottom`), measured once at startup and on every resize/`visualViewport` change into the CSS custom properties `--real-safe-top` / `--real-safe-bottom` on `<html>`. Every screen's own spacing must read ONLY those two variables — never `env()` directly, and never `insets.top`/`insets.bottom` (which are now correctly, permanently zero on web, so using them for standalone spacing is simply a no-op bug waiting to happen again). Two established techniques, both already wired through this pair:
- A web-only filler `View` with a `nativeID` (see `SafeAreaTopFill.tsx` / `SafeAreaBottomFill.tsx`), sized entirely by a CSS rule keyed to that id — `height: var(--real-safe-top, 0px)` or `var(--real-safe-bottom, 0px)` — never a numeric RN style.
- For a screen that already carries its own flat "ordinary browser chrome" padding/position (predating `SafeAreaTopFill`), a dedicated CSS override on that same id adding the real inset via `calc()` — e.g. `padding-top: calc(60px + var(--real-safe-top, 0px)) !important` — instead of stacking a separate fill element on top of it.

Both resolve to `0px` (no change at all) in ordinary browser chrome and the real inset in standalone mode.

Any new full-screen layout or modal that reaches the physical top or bottom edge must use one of these techniques (reading `--real-safe-top`/`--real-safe-bottom`, never `env()` or `insets.*` directly), and must pass the standalone-simulation Playwright check (`npm run verify:standalone-safe-area`) before being considered done. That suite forces `--real-safe-top`/`--real-safe-bottom` directly (so every legitimate consumer responds together), asserts the topmost content on every key screen sits at the EXACT expected offset (not "at least"), asserts exactly one top/bottom fill is actually visible per screen, and greps the production build output to confirm `env(safe-area-inset` appears nowhere except the two sanctioned probe rules.

## Safe-area fills are paint, not controls

A real installed-iPhone bug (Doc's Stories' top-left back button and top-right X not responding to taps) traced back to `SafeAreaTopFill`/`SafeAreaBottomFill` painting over controls and winning hit-testing simply by being large and present. Every fill element (`SafeAreaTopFill.tsx`, `SafeAreaBottomFill.tsx`, and the two hidden probe pairs in `public/index.html`) carries `pointerEvents="none"` / CSS `pointer-events: none`, app-wide, permanently — a fill must never be able to intercept a tap meant for whatever it's layered near. Any new fill element must do the same.

Beyond the shared fills, a screen that manages its own top padding (e.g. `StoryViewer.tsx`'s `calc()`-based override) can still bury a control: an absolutely-positioned sibling's `top` offset is measured from the CONTAINER'S OWN top edge, not from after the container's `paddingTop` is applied — so a flat `top` value that doesn't account for the real safe-area inset can genuinely overlap a header row once the inset is large enough, and a later-in-DOM, pointer-events-`auto` sibling (like a full-bleed tap zone) wins hit-testing over it by default. Give the control's row an explicit `zIndex` higher than any such sibling so it always wins regardless of the exact overlap math.

`scripts/verify-standalone-safe-area.js` guards this directly: with real insets forced, it hit-tests the story viewer's close button, the tab bar's four tabs, and the group chat send button at their visual centers and asserts the control itself (or a descendant) receives the tap — never a fill or overlay. Any new interactive control added near a safe-area fill should get the same check. Because `pointerEvents="none"` compiles to a `!important` CSS rule in react-native-web, the suite's own paint-stacking checks (`countVisibleTopSafeAreaElements`, the bottom-edge-color check) have to temporarily flip a fill's `pointer-events` to `auto` with matching `!important` priority — via `el.style.setProperty('pointer-events', 'auto', 'important')`, restored before the call returns — purely as a measurement technique; a plain property assignment loses to the stylesheet rule silently.

## Tab bar bottom density: flex-stretch slack is invisible to the eye, not to the DOM

A tab bar whose own padding and height constant look modest can still render far taller than intended, because `@react-navigation/bottom-tabs`'s web output stretches each `<a role="tab">` to the tab row's full cross-axis height (`align-items: stretch`) regardless of how much vertical space its own content (icon + active-dot + label) actually needs. With the row taller than that content and `justify-content: flex-start` packing from the top, the leftover space lands BELOW the label as pure dead space — invisible to a glance at the stylesheet (no padding/margin value says "10px of nothing here"), but very visible to a person's eye as "the bar feels tall." `TAB_BAR_CONTENT_HEIGHT` in `tabBarHeight.ts` is the one constant to tune: measure the tab row's actual DOM height (`[role="tablist"]`'s `getBoundingClientRect()`) against the deepest tab item's own content height (its text label element's `getBoundingClientRect()`/`scrollHeight`, which must stay equal to each other — if `scrollHeight` ever exceeds the rendered rect, the label itself is being clipped, not just the slack trimmed) before changing this constant, not just by eyeballing a screenshot — a few pixels of margin between those two numbers is deliberate breathing room; sizing the row to exactly the content height removes the dead space without touching any icon, label, or padding.

This app's own `ScreenOverlay` (used by Messages, Memberships, the hamburger drawer, and every other secondary full-screen panel) reads `useTabBarHeight()` to stop its own box short of the real tab bar — that coupling is automatic and needs no separate update when `TAB_BAR_CONTENT_HEIGHT` changes. `ScreenContainer`'s own flat scroll `paddingBottom` (used by all four tab screens) is NOT coupled to the tab bar's height at all and doesn't need to be: react-navigation lays out a tab's screen content and the tab bar box as separate, non-overlapping flex siblings, so shrinking the bar only grows the screen's own content area — it can never cause content to end up hidden underneath the bar.

`scripts/verify-standalone-safe-area.js`'s `[tab-bar-density/*]` checks guard the actual number a person looks at: the gap between a tab's own label and the physical viewport bottom, in both ordinary browser chrome (should land near a flat ~12px baseline) and forced-inset standalone simulation (should land near `forced inset + 12px`) — plus a direct clipped-label check (comparing the label's `scrollHeight` to its rendered height) so a future over-aggressive cut fails loudly instead of silently truncating a label.

## Viewport lock: no pinch zoom, no double-tap zoom

A real installed-iPhone bug found that pinch-zooming the standalone app scales the whole layout, unglues the fixed top bar and tab bar from the viewport, wrecks the bottom safe-area spacing, and can leave the page subtly zoomed afterward — Skool and other native-feeling apps never allow interface zoom at all, and this app now matches that. The lock is three independent, deliberately redundant layers in `public/index.html`:

1. **The viewport meta** (`maximum-scale=1, user-scalable=no`, alongside the existing `width=device-width, initial-scale=1, viewport-fit=cover`). The primary lock, and the one iOS actually respects reliably — but only in home-screen standalone mode (this app's real target); ordinary browser Safari can ignore `user-scalable` for accessibility reasons, which is why layers 2 and 3 exist.
2. **`gesturestart`/`gesturechange`/`gestureend` listeners on `document`**, each calling `preventDefault()` with `{ passive: false }`. These are WebKit's own non-standard events for a two-finger pinch/rotate, fired independently of ordinary touch events — stopping the browser's own native PAGE-zoom gesture from ever starting, regardless of what the viewport meta says.
3. **`touch-action: pan-x pan-y` on `html`/`body`**. Permits ordinary single-finger scrolling in both directions but deliberately excludes the named `pinch-zoom` value, so a two-finger touch never gets claimed by the browser for its own zoom and falls straight through to this app's own touch handlers instead.

None of these three touch this app's own INTENTIONAL two-finger gestures — `MediaViewer.tsx`'s photo pinch-zoom and `ProfilePhotoCropModal.tsx`'s crop pinch-zoom both read raw touch events (`onTouchStart`/`PanResponder`), a completely separate event family from WebKit's gesture events, and `touch-action` only controls which gesture the *browser* claims natively, never whether JS still receives the underlying touch events. `ProfilePhotoCropModal` additionally sets `body.style.touchAction = 'none'` directly (an inline style, which always wins over the stylesheet rule above regardless of specificity) only while its own crop frame is open, for total touch exclusivity beyond just pinch-zoom, and restores whatever was there before on close. Any new screen that wants its own two-finger gesture should follow the same pattern — raw touch events, not a dependency on the browser's native pinch-zoom being available, which this lock removes app-wide.

`window.visualViewport.scale` is also tracked (into the CSS custom property `--viewport-scale`, inside the same `syncOffsetAndInsets()` function that already recomputes `--real-safe-top`/`--real-safe-bottom`/`--app-offset-top` from scratch on every resize/visualViewport event) as a belt-and-suspenders check for the rare iOS version where a scale change slips through anyway — there is no separate "recovery" step needed because nothing in this pipeline ever caches a scale-dependent value; the next event after scale returns to 1 reads the real numbers again on its own.

## iOS input zoom: every text field needs an effective font-size of at least 16px

iOS Safari auto-zooms the whole page when a focused input's font size resolves under 16px — a silent trigger the viewport lock above cannot override (it's a separate iOS behavior, not a pinch/scale gesture). Every `TextInput` in this app must resolve to `fontSize: 16` or larger; where a design wants visually smaller text, the correct technique is a 16px font with a CSS `transform: scale()` applied for display, never a sub-16px `fontSize` directly. A full audit (round 11) found three real offenders, all now fixed: `GifPicker.tsx`'s search field (was 14), `DocsGroupChatScreen.tsx`'s pinned-prompt editor (was 14), and its main composer on mobile (was 15 — desktop was already 17). The group chat composer's `lineHeight` and `MIN_INPUT_HEIGHT`/`MAX_INPUT_HEIGHT` constants (which derive the composer's one-line/five-line auto-grow sizing directly from the line-height number) were updated in lockstep — changing a composer's `fontSize`/`lineHeight` without also updating any height constant derived from the old `lineHeight` is exactly how a round like this can silently reintroduce a different bug (a clipped first line) while fixing this one.

`scripts/verify-standalone-safe-area.js`'s `auditInputFontSizes()` walks every visible `<input>`/`<textarea>` on a page and asserts each one's COMPUTED font-size (not its authored style — catches anything inherited or overridden differently than the source implies) is at least 16px, run against the sign-in screen, the create-post composer, search, and the group chat composer. Any new screen with a text field should get the same check rather than relying on a one-time manual audit.

## Keyboard regression: 100dvh doesn't shrink for the on-screen keyboard

Round 8 replaced a JS-measured `--app-height` with plain `100dvh` for `#root`'s own sizing — correct for Safari's collapsing/expanding toolbar, which `100dvh` is defined to track, but a real device confirmed it does NOT shrink for the on-screen software keyboard the old JS measurement used to. The keyboard instead only shrinks `visualViewport.height` and pans `visualViewport.offsetTop` (which Round 5's `--app-offset-top` already compensates for at the `#root` level). A bottom-anchored composer — one pinned to the bottom of a flex column, not scrollable in-flow content — sits at the bottom of the FULL, un-shrunk `#root`, which the keyboard now geometrically covers with nothing of its own compensating: on a real installed iPhone, the group chat and comment composers were completely hidden behind the open keyboard.

**The fix:** `--keyboard-inset` (computed in `public/index.html`'s `syncOffsetAndInsets()`, alongside `--app-offset-top`/`--real-safe-top`/`--real-safe-bottom`/`--viewport-scale` — one function, one set of listeners, for every viewport-derived CSS variable) = `max(0, window.innerHeight - visualViewport.height - visualViewport.offsetTop)`: exactly how much of `#root`'s own full height the keyboard is covering that the visual viewport's own pan didn't already reveal. A bottom-anchored composer reads it via a dedicated `nativeID` (`#group-chat-composer-keyboard-rise`, `#doc-thread-composer-keyboard-rise`, `#post-detail-composer-keyboard-rise`) and rises by that exact amount via `transform: translateY(calc(-1 * var(--keyboard-inset, 0px)))` — never a layout property, so it never affects a sibling's position or triggers reflow. It's a no-op (0px) whenever the keyboard is closed, which is also what returns the composer to its normal position — directly on top of its own safe-area fill above it in the same flex column — the instant the keyboard closes; there's no separate "restore" step. **`#root`'s own sizing stays plain `100dvh`, untouched** — this fixes only the composers that need to react to the keyboard, not the shell itself, which Round 8 already got right for everything else.

**One mechanism only, deliberately.** A round briefly added `interactive-widget=resizes-content` to the viewport meta — the CSS Viewport spec's own declarative answer to this same problem — on the theory that it was a safe, ignorable-if-unsupported fallback alongside `--keyboard-inset`. It was removed again: on an iOS version that DOES honor it, the OS's own viewport resize and the JS `--keyboard-inset` rise both fire for the same keyboard open/close and fight each other, which is exactly what a real device described as the screen shrinking repeatedly while typing. `--keyboard-inset` is the only keyboard-compensation mechanism in this app; do not reintroduce `interactive-widget` (or any other declarative/automatic keyboard-resize opt-in) alongside it. `scripts/verify-standalone-safe-area.js` asserts the built viewport meta never contains the string `interactive-widget` for exactly this reason.

Any new screen that adds a genuinely bottom-anchored (not inline-scrollable) text input must give its composer row a `nativeID` and the same `#*-keyboard-rise` treatment in `index.html` — a plain in-flow input inside an already-scrollable container (CreatePostModal's title/body, Log Results, Invite a Friend, Search — none of them pinned to a screen edge) doesn't need this, since the browser's own native focus-scroll-into-view already keeps it clear of the keyboard; CreatePostModal still gets a defensive `padding-bottom: var(--keyboard-inset, 0px)` on its scroll content as insurance for a very tall entry, not because it's a confirmed instance of this bug.

**Round 15 replaced `--keyboard-inset` as what actually positions the three composers**, after a real installed-standalone iPhone's own LAST KEYBOARD SNAPSHOT (see "The hidden debug overlay" below) caught the formula computing `0px` while the keyboard genuinely covered 62px of the composer. Reconstructing the capture: `innerHeight` and `visualViewport.height` had both collapsed to the same `471` (the keyboard shrinks the *layout* viewport too in this condition, not only the visual one, contrary to the "Round 8" assumption above that only the toolbar does that), with `offsetTop` panned to `341` — but `--keyboard-inset`'s `fullHeight` term read back `window.innerHeight` (`471`) instead of the `100lvh` probe's still-correct `874`, because its `matchMedia('(display-mode: standalone)').matches` branch, evaluated fresh inside the resize handler, didn't reliably select the standalone branch at that exact instant. `471 - 471 - 341` clamps to `0` — a wrong answer that happened to look like a plausible one. The formula's real flaw was never the one wrong number on one device; it's that it has to correctly *predict* "how tall is the shell right now" from a live media-query match before it can compute anything.

**The fix: measure instead of predict.** `public/index.html`'s `applyComposerKeyboardRise()` reads the composer's own current, untranslated bottom edge (`transform: none`, then `getBoundingClientRect()`) and the visual viewport's own current bottom edge (`visualViewport.offsetTop + visualViewport.height`) in the same layout-viewport coordinate space, and sets `transform: translateY(...)` to exactly the difference (clamped to never push the composer down past its natural position) — as a JS-applied inline style, not a CSS rule reading a formula. This is immune to whether iOS shrinks `innerHeight`, pans `offsetTop`, or both, and immune to which media query matches when, because it never asks "how tall is the full shell" at all — only "where are these two edges right now." It runs on every `visualViewport` `resize`/`scroll` event, every window `resize`/`orientationchange`/`load`/`pageshow`, and every `focusin` (so a composer that mounts, or gains focus, while the keyboard is already open positions correctly without waiting for a geometry event). `--keyboard-inset` itself is unchanged and still drives `CreatePostModal`'s defensive scroll padding — only the three composers stopped trusting it for their own position.

`scripts/verify-standalone-safe-area.js`'s `checkKeyboardRise()` now stubs `visualViewport.height`/`.offsetTop` directly (an ordinary, configurable WebIDL attribute pair, shadowed with own, configurable properties — the same technique `forceVisualViewportShrink()` uses for the standalone-`100lvh` and keyboard-snapshot checks) to the exact real-device numbers (`471`, `341`) and dispatches a real `resize` event, then asserts the composer's rendered bottom lands exactly on the stubbed visual bottom edge (`812`), and returns to its original bottom once the stub is removed — exercising the unmodified production listener end to end, anchored to the actual failure rather than a round-number stand-in.

**Round 16: the measurement was right, the delivery wasn't — the rise has to survive React re-rendering the composer.** A later real-device capture confirmed Round 15's own measurement was exactly correct (visual bottom `471`, composer natural bottom `874`, applied `translateY` `-403` — precisely `874 - 471 = 403`). But a screenshot moments later showed the composer back under the keyboard anyway. The bug was never in the math: Round 15 delivered its result as `el.style.transform`, an inline style written directly onto the exact React-rendered `View` node — and `DocsGroupChatScreen`/`DocThreadView` both re-render that same node on every keystroke (the composer's own auto-grow height state). That re-render reapplies the node's `style` prop, which wipes whatever `transform` this function had set out-of-band a moment earlier. (Checked directly: neither render path ever puts its own `transform` in that `View`'s style prop — the slot was never fought over on purpose, it was simply being reset to nothing by the ordinary act of re-rendering.)

**The fix: stop writing to the composer's own inline style at all.** `applyComposerKeyboardRise()` now sets a single, document-root CSS custom property — `--composer-rise` (one shared variable, same convention as `--keyboard-inset`: only one of the three mutually-exclusive composers is ever mounted at a time) — and a stylesheet rule in `public/index.html`, keyed to the three composer ids (the same shape as the Round 12 rule Round 15 removed, just reading a measured variable instead of a predicted formula), reads it: `transform: translateY(calc(-1 * var(--composer-rise, 0px)))`. React re-rendering the composer node can still rewrite that node's *own* style attribute every keystroke, exactly as before — but it has no reason to ever touch `:root`'s style, and the stylesheet rule itself lives in this file's `<style>` block, entirely outside React's reach. The measurement step changed to match: `naturalBottom` is now read with `--composer-rise` temporarily zeroed (not the element's own style cleared), since the rule — not an inline style — is what would otherwise still be translating the rect being measured.

**Self-healing while the keyboard is open.** A light `setInterval` guard (250ms, not a `requestAnimationFrame` loop — this only needs to catch drift a person could perceive, not match frame timing) runs only while a rise is actually applied, re-measuring the composer's actual on-screen bottom against the visual viewport's own bottom and re-running the full measurement if they've drifted by more than 2px — a backstop against any future clobber path this round didn't imagine (a content-growth layout shift mid-keystroke, a browser quirk), not a fix for a second confirmed bug. It starts/stops itself from inside `applyComposerKeyboardRise()` based on whether the current rise is nonzero, so there's no separate lifecycle to manage.

`scripts/verify-standalone-safe-area.js`'s `checkKeyboardRise()` grew the exact regression check this bug needed: after confirming the rise, it types into the composer's own input (`group-chat-input` / `message-draft-input`) — forcing the same React re-render a real keystroke does — and asserts the composer's rendered bottom is *still* on the stubbed visual bottom edge afterward. The old inline-style delivery would have failed this check; the stylesheet-rule delivery passes it unconditionally, because typing can rewrite the composer node's own style all it wants without ever touching `--composer-rise`.

**Round 17: three real-device snapshots on the same iPhone, same day, proved the per-composer approach itself was the wrong shape of fix — and replaced it with a shell-level resize.** Rounds 15 and 16 each correctly fixed the specific capture that motivated them and were each then undone by a *different* real-device report. The reason became clear once three snapshots were compared side by side:

| | `innerHeight` | `visualViewport.height` | `offsetTop` |
|---|---|---|---|
| Regime A | `874 → 471` | `471` | `341` |
| Regime B | stays `874` | `471` | `0` |
| Regime C (different input) | `725` | `471` | `149` |

`innerHeight` disagrees with itself across identical-looking "keyboard open" moments on the *same device* — sometimes the keyboard shrinks the layout viewport (Regime A), sometimes it doesn't (Regime B), sometimes it lands somewhere in between (Regime C). That instability is exactly how Round 15's `matchMedia`-timing bug and Round 16's React-clobbered-transform bug both slipped through: neither fix's correctness depended on `innerHeight` directly, but `--keyboard-inset`'s own formula (still computed, see below) does, and chasing "the composer" rather than "the shell" meant every fix was scoped to one regime's symptom. `visualViewport.height` is the one number that read `471` in all three — the keyboard's effect on what's actually *visible* is the one truly stable fact across every capture, which is exactly the number browser Safari itself resizes the layout viewport to natively (the real reason this class of bug is never reported there: "In regular Safari everything works natively because the layout viewport resizes and bottom-anchored UI reflows").

**The fix: resize the shell, not the composer.** `public/index.html`'s `syncKeyboardShellMode()` replaces `applyComposerKeyboardRise()` (and its self-healing guard, and `--composer-rise`) entirely — there is no composer-specific code left anywhere in this mechanism. While `window.matchMedia('(display-mode: standalone)').matches` is true and `visualViewport.height` reads more than 100px below the `100lvh` probe's rest value, it sets `data-keyboard-shell="open"` on `<html>` and a `--shell-keyboard-height` custom property to `visualViewport.height` exactly. A CSS rule just below the `@media (display-mode: standalone)` block — `html[data-keyboard-shell='open'] #root { height: var(--shell-keyboard-height); }` — resizes `#root` to match. `#root`'s own pre-existing `transform: translateY(var(--app-offset-top, 0px))` (Round 5) keeps translating it by `visualViewport.offsetTop` with no change needed at all, since that's the exact same number either way — one less variable computing the same thing twice. Every bottom-anchored flex child — composers, the tab bar, sheets, anything — reflows to the shrunk shell's own bottom edge through ordinary CSS flexbox, the same way they already reflow to `#root`'s normal height the rest of the time. The three `#*-composer-keyboard-rise` `nativeID`s on the composer rows are left in place (harmless, and useful as measurement anchors in the test suite) but nothing — no CSS rule, no JS — reads them as rise targets anymore.

**Why this rule is deliberately *not* nested inside `@media (display-mode: standalone)`.** The JS already gates on that exact media query before ever setting the attribute or the variable; stacking a second CSS-level media-query gate on top of a mechanism built specifically to stop depending on live media-query timing (Round 15's whole lesson) would be trusting the thing this round replaced. The attribute selector on `html` is the single source of truth, and that's also what makes the reset structural rather than a cleanup step that has to run and has to get every property right: the instant `syncKeyboardShellMode()` removes the attribute, this rule stops matching at all, and `#root` falls straight back to the plain `100lvh` rule above it, with nothing left over to reset by hand.

**Reset correctness, with real backstops.** `syncKeyboardShellMode()` runs from every `visualViewport` `resize`/`scroll`, every window `resize`/`orientationchange`/`load`/`pageshow`, every `focusin` (an input gaining focus while the keyboard is already open needs its own trigger, independent of a geometry event), every `focusout` (a keyboard-close path where blur fires before iOS has actually resized the visual viewport back — delayed 50ms to give the OS a moment to do that resize first), every `visibilitychange` (backgrounding/resuming can leave stale state with no clean `visualViewport` event pair), **and** an always-on 250ms `setInterval` that is never started or stopped based on current mode — Round 16's own start/stop guard was itself one more piece of state that could in principle drift, and this round's whole point is fewer moving parts, not more. The interval is the backstop of last resort: whatever causes an explicit trigger to misfire or not fire at all, the shell is never more than 250ms away from the correct state regardless. This is also the direct fix for a real, separately-confirmed symptom — the bottom tab bar left visibly "chopped" at the screen edge after dismissing the keyboard on the search screen (which has no composer-rise id at all, ruling out anything composer-specific as the cause) — a leftover-offset reset leak that this backstop set structurally cannot leave uncorrected for more than one tick.

**Scope: standalone only, deliberately.** `syncKeyboardShellMode()` is a no-op in ordinary browser tabs — real mobile Safari's own native layout-viewport resize already produces the correct reflow there, and no bug report in this entire engagement has ever been about an ordinary browser tab. `--keyboard-inset` itself is untouched and still drives `CreatePostModal`'s defensive scroll padding; it simply has no connection to the shell mechanism anymore.

**Testing note: a better technique than Round 13's CSS-forcing workaround, for a mechanism this load-bearing on `matchMedia`.** Chromium's CDP `Emulation.setEmulatedMedia` still doesn't honor `display-mode` in this environment (unchanged from Round 13's own finding), but this round's mechanism is JS that calls `window.matchMedia()` itself, not just CSS — so `scripts/verify-standalone-safe-area.js`'s `forceStandaloneDisplayMode()` overrides `window.matchMedia` directly via `page.addInitScript()` (in place before the app's own inline script ever runs), answering `true` for exactly the display-mode query and passing every other query through to the real implementation unchanged. This does **not** make the browser's own CSS engine start matching a real `@media (display-mode: standalone)` block — that's a separate evaluation path this override can't reach, which is exactly why the shell-override rule above is deliberately not nested inside that media query — but `syncKeyboardShellMode()` and `syncOffsetAndInsets()` only ever ask JS's `matchMedia()`, so this exercises their real, unmodified gating logic end to end, which the old CSS-forcing technique never could.

`runKeyboardShellRegimeCheck()` drives all three regimes (A, B, and C verbatim, against group chat; Regime A again against Message Doc for cross-composer coverage) through the real, unmodified production listener and asserts every hard requirement this round needed: the shell resizes to exactly `visualViewport.height` while completely ignoring `innerHeight`; `#root`'s rendered box sits exactly on the visual viewport's own top/bottom; the focused composer area stays fully inside it; it survives a forced React re-render (typing); closing the keyboard resets pixel-exact; and a **second** open/close cycle still matches the very first at-rest reading, catching drift a single cycle would miss. A dedicated `[keyboard-shell/search-screen]` block reproduces the reported chopped-tab-bar scenario directly — open the search overlay (no composer id involved at all), force the keyboard open, close it, close the overlay, and assert both `#root` and the tab bar itself land back exactly at the true physical bottom edge.

## Standalone-only: 100dvh undershoots the real screen, use 100lvh there

A real installed iPhone, measured directly via the debug overlay, showed `100lvh` resolving to `874px` while `100dvh`/`visualViewport.height`/`window.innerHeight` all agreed on a shorter `860px` — and `#root`/`html`/`body`/every fill ended exactly at 860, leaving a 14px band of the page's own background color below everything, down to the true physical screen edge. An earlier round's own comment in `index.html` assumed `dvh`/`svh`/`lvh`/`vh` "should read identical in standalone mode, where there's no toolbar to collapse" — that assumption was simply wrong, which is the entire reason the debug overlay's probe comparison exists rather than trusting it. `100dvh` is DEFINED to track Safari's collapsing/expanding toolbar; there is no toolbar at all in standalone (no address bar, nothing to collapse), so "dynamic" has nothing correct to track there, and iOS was reserving that dynamic space without ever using it.

**The fix:** `public/index.html` now has an `@media (display-mode: standalone) { ... }` block, placed after the base `html`/`body`/`#root`/`#welcome-screen-root`/`#about-screen-root` rules, that re-declares each of those same selectors' height/min-height with the same fallback-chain technique (`100%`, then `100vh`, then — in this block only — `100lvh` instead of `100dvh`). Equal specificity, later source order: the cascade's own tiebreak is what applies the override, not `!important`, not a separate mechanism. **Ordinary browser tabs are intentionally untouched** — the base rules keep their unmodified `100dvh` fallback chains exactly as they were, because there a real Safari toolbar genuinely does come and go and `100dvh` is the correct unit to track it with. Any new full-screen sizing rule (a future `#some-screen-root { min-height: ... }`) that needs to behave correctly in standalone must get the same two-rule treatment — a base `100dvh` chain for ordinary browsers, and a same-selector override inside this `@media` block ending at `100lvh` — not a single rule trying to serve both environments at once.

`--keyboard-inset`'s own formula (see "Keyboard regression" above) was updated to match: its "full height" term is `window.innerHeight` in ordinary browser tabs (where `#root` is still `100dvh` and `window.innerHeight` already agrees with it), but in standalone it reads the same `#debug-probe-100lvh` element the debug overlay's own report already uses — one measured value, two consumers, not a second independent measurement of the same thing. Using `window.innerHeight` (860) as "full height" in standalone, now that `#root` is actually 874px tall there, would under-rise every composer by that same 14px gap on top of whatever the real keyboard height is.

**Testing note:** Chromium's CDP `Emulation.setEmulatedMedia` does not honor `display-mode` as an overridable feature in this environment (confirmed directly — the identical `features` array call DOES flip `prefers-color-scheme`, so this is specific to `display-mode`, not a broken mechanism), so `scripts/verify-standalone-safe-area.js` cannot make the real `@media (display-mode: standalone)` block actually match from a test. It instead checks both halves separately: a static check brace-matches the real rule's own source text in the built output (search for the literal `@media (display-mode: standalone) {`, not the bare phrase, which this file's own prose comments also legitimately contain) and asserts it sizes the right selectors and never still mentions `100dvh`; a behavioral check forces the identical declarations directly via `addStyleTag` (the same "force what the real mechanism would produce" technique `FORCE_INSET_CSS` already uses throughout this file) and asserts `#root`'s rendered height matches the resolved `100lvh` probe value exactly, and that the bottommost physical pixel is the tab bar fill's own color with no page-background strip beneath it.

## The hidden debug overlay

Three real-device bugs found after Round 17's keyboard shell fix landed. No database changes in this round.

**Search screen layout: chopped tab bar at rest, bleed-through with the keyboard open.** `ScreenOverlay.tsx`'s own top comment lists which secondary screens deliberately stop short of the bottom tab bar (`bottom: tabBarHeight` instead of `bottom: 0`) so the real tab bar stays visible and tappable underneath — correct for Profile, My Workouts, Close Friends, the Boathouse schedule, Messages, none of which take over the keyboard. **Search results now deep-link to their exact destination, and deck cards are completion-gated.** `SearchModal.tsx`'s old `handleSelect` only ever called `navigation.navigate(result.tab)` — a bare tab switch, which is why a deck card result landed on The Deck tab in whatever mode it defaulted to (Shuffle), never the card itself. **A known, pre-existing, unrelated gap this round did not touch:** `CommunityContext.tsx`'s `addTextPost` stores a web-picked photo's `media_url` as the raw `blob:` object URL `URL.createObjectURL()` returns, never uploaded to durable storage — this renders correctly within the same browser session/page (which is what both the real-device report and this round's own Playwright check exercise), but a `blob:` URL is only ever valid for the document that created it, so the photo would fail to load on reload or from any other device/session. **2. The composer photo preview's `aspectRatio`-box fix from a prior attempt was structurally correct but never actually refined — a real browser quirk, caught by this round's own test before it ever reached a device.** The brief for this item called for replacing `Image.getSize()` with the web `<img>` element's own `onLoad` natural dimensions, reasoning that `Image.getSize()` might be silently failing to resolve for a real device's blob/data-URI photo. Implementing that literally — reading `e.nativeEvent.target.naturalWidth`/`naturalHeight` off react-native-web's `Image` `onLoad` callback — produced a preview that never refined past its `DEFAULT_PREVIEW_RATIO` placeholder in this suite's own PNG fixture check, which caught it immediately (the PNG fixture's real 1.5 ratio never appeared; the box stayed at the 4:3 default forever).

Root-caused directly (see the isolated reproduction below): `react-native-web`'s `ImageLoader.load()` always routes its `onLoad` callback through `image.decode().then(onDecode, onDecode)` before calling it — an async hop of (at minimum) one microtask after the image's own native `load` event fires. A plain `new window.Image()` test confirmed `e.target === img` is `true` *synchronously inside* `onload`, but `false` one microtask later, after `.decode()` resolves:
```js
img.onload = (e) => {
  console.log(e.target === img);                 // true
  img.decode().then(() => console.log(e.target === img)); // false
};
```
This is a genuine browser behavior (Chromium nulls — or otherwise invalidates — a dispatched Event's `target` once its task has fully unwound, even though nothing in the DOM Events spec requires this), not a react-native-web bug, but react-native-web's own `onLoad(e)` forwards exactly that now-stale event as `nativeEvent`, so **any** `onLoad` handler built on `nativeEvent.target` on web is unconditionally broken, regardless of what triggered the load. This also means `Image.getSize()`'s own apparent real-device failure (the premise behind this round's instructions) likely has a different, narrower cause than "the whole mechanism never resolves" — `ImageLoader.getSize()` doesn't read `e.target` at all; it polls the underlying `Image` object's own `naturalWidth`/`naturalHeight` directly on a 16ms interval, which is unaffected by the event-staleness bug above.

**The fix:** `MediaAttachmentPicker.tsx` no longer touches `nativeEvent.target` (or react-native-web's `Image` `onLoad` prop) at all. On web, it creates its own `new window.Image()` probe and reads `naturalWidth`/`naturalHeight` directly off that object inside its own synchronous `onload` — the ordinary, textbook way to use this browser API, and immune to the exact staleness trap above since it never dereferences the load event itself. This is still genuinely "the web image onLoad natural dimensions," just applied directly instead of through react-native-web's broken indirection. Native keeps calling `Image.getSize()` (no known issue there — the staleness bug is specific to react-native-web's `decode()`-then-event-forwarding sequence, which doesn't exist on native platforms). The `DEFAULT_PREVIEW_RATIO` / CSS `aspectRatio` box from the prior attempt is unchanged and still does the real load-bearing work: the preview can never be zero/blank regardless of whether this refinement step ever fires.

`scripts/verify-standalone-safe-area.js`'s `[photo-preview/composer]` block now checks both fixtures end to end: the existing 300×200 PNG (ratio 1.5) and a new, genuinely large, genuinely decodable baseline JPEG at real iPhone-photo resolution (4032×3024, encoded via `jpeg-js` — added as a devDependency purely for this fixture, never shipped in the app bundle — the same "a real decodable file, not a hand-assembled byte string" standard `buildSolidPng` already set for the PNG fixture, just for a format a from-scratch encoder would be far riskier to hand-roll correctly). Both fixtures are delivered through Playwright's real `filechooser` event onto a real `File` object, exactly mirroring `useMediaPicker.ts`'s own `URL.createObjectURL(file)` web path — there was never an "abstraction over a blob URL" to replace; the real device path was already being exercised, which is part of why this bug needed an actual root-cause fix rather than a fixture-delivery change. For each fixture the suite asserts the preview paints nonzero within ~150ms (well under the "within a second" bar, and before any load/decode could plausibly resolve — proof the DEFAULT box, not the refinement, is what's painting) and separately, after real decode time, that it refines to the fixture's own exact ratio (1.5 for the PNG, 4:3 for the large JPEG) — the large-JPEG refinement check is the one that would have caught this round's own bug: with the broken `nativeEvent.target` approach it silently passed anyway, because `DEFAULT_PREVIEW_RATIO` (4:3) and the JPEG fixture's real ratio (also 4:3) happen to coincide, which is exactly why the PNG fixture (a deliberately different ratio, 1.5) is the one that actually exposed the bug — a reminder that a fixture whose "refined" and "default" values can coincide can't tell a working refinement mechanism from a silently broken one.

## Round 23: 12-hour clock everywhere — the real gap was two ADMIN INPUT fields, not any display surface

A full sweep for every place the app renders a time of day — post/comment timestamps, group chat messages, class schedule, the Weekly Challenge timing line, the Founding 50 deadline, Log Results, admin screens, booking confirmations — found that every DISPLAY surface was already correct: `formatEtTime()` (`challengeSchedule.ts`), group chat's own `timeLabel()`, and Content Library's own `formatReleaseAt()` all render via `toLocaleTimeString`/`Intl.DateTimeFormat` with the `en-US` locale, which defaults to 12-hour AM/PM even without `hour12` ever being passed explicitly. The actual, genuine 24-hour surfaces were two admin-facing TYPED INPUT fields that round-trip through a human reading and retyping a clock time: `FoundingFiftyAdminScreen.tsx`'s START TIME/END TIME fields (placeholder `HH:MM (24-hour)`, e.g. `23:59`) and `ContentWorkoutForm.tsx`'s single-entry RELEASE TIME field (placeholder `HH:MM`, with an explicit "24-hour time, e.g. 06:00 or 18:00." hint) — a typed/prefilled field is a rendering of time in the same spirit as any read-only text, and these were the two places a member-facing admin would actually have to think in military time.

**The fix, admin inputs:** `FoundingFiftyAdminScreen.tsx`'s `etTimeStrOf()` now formats the prefilled value as `H:MM AM/PM` (`hour % 12 === 0 ? 12 : hour % 12`, plus an `AM`/`PM` suffix from `hour < 12`), and `parseEtParts()` now parses that same shape back (`/^(\d{1,2}):(\d{2})\s*([AaPp][Mm])$/`, with `12 AM` folding to hour `0` and `12 PM` staying `0` before the existing `+12` PM step) instead of a bare 24-hour `HH:MM`. `ContentWorkoutForm.tsx`'s `timeStrOf()` got the identical 12-hour conversion for its own prefill; its parsing didn't need a code change at all — `parseReleaseAt()` (`contentLibraryParser.ts`) already accepted an optional `AM|PM` suffix alongside bare 24-hour input (`/^(\d{4})-(\d{1,2})-(\d{1,2})\s+(\d{1,2}):(\d{2})\s*(AM|PM|am|pm)?$/`), so only the surrounding placeholder/hint/error copy needed updating to model the format members should actually type. The bulk-import parser's own example text and error copy (`contentLibraryParser.ts`'s `BULK_IMPORT_EXAMPLE` and `parseBlock()`'s date-error message) were updated the same way, for the same reason — copy modeling 24-hour input trains an admin to type it, even where the parser itself was already lenient.

**Hardened, not fixed:** the three display formatters that were already correct (`formatEtTime`, group chat's `timeLabel`, Content Library's `formatReleaseAt`) each got an explicit `hour12: true` added to their `Intl`/`toLocaleTimeString` calls — previously correct only because the `en-US` locale happens to default that way, which is exactly the kind of implicit behavior a future locale change, copy-paste into a non-`en-US` context, or library upgrade could silently flip to 24-hour with zero warning. A 12-hour clock being a deliberate house rule means it should never again depend on an unstated default.

`scripts/verify-standalone-safe-area.js` gained two layers of guard, the house's usual static-plus-behavioral pairing. **Static** — `auditTwelveHourClock()` greps the built JS bundle for five specific old 24-hour placeholder/hint/error strings (`'HH:MM (24-hour)'`, `'24-hour time, e.g. 06:00 or 18:00.'`, `'YYYY-MM-DD and HH:MM (24h)'`, etc.) and asserts none remain anywhere, and that the replacement 12-hour strings (`'H:MM AM/PM'`, `'12-hour time, e.g. 6:00 AM or 6:00 PM.'`) actually shipped. **Behavioral** — a new `[12-hour-clock/*]` block proves real RENDERED time values, not just placeholder text, come out 12-hour: it sends a real group chat message and asserts the row's own timestamp matches `/\b(1[0-2]|[1-9])(:[0-5]\d)?\s?(AM|PM)\b/` and never `/\b([01]\d|2[0-3]):[0-5]\d\b(?!\s?(AM|PM))/` (the minutes group is deliberately optional in the 12-hour pattern — `formatEtTime()` itself omits `:00` on an exact-hour time, e.g. `SATURDAY 12 PM ET`, which is still correctly 12-hour, not a regression); seeds a published Content Library entry directly into `contentLibraryDrafts.v1` (the real seed ships every entry as a DRAFT, so a fresh profile never has a "current" Weekly Challenge at all without this) and reads the live `challenge-open-timing`/`challenge-closed-timing` line; and seeds a known Founding 50 window (`2027-01-15T14:30:00.000Z` / `2027-01-20T04:59:00.000Z`, both January so there's no DST ambiguity) and asserts the admin screen's `#founding-fifty-start-time`/`#founding-fifty-end-time` fields prefill to exactly `9:30 AM` / `11:59 PM`.

Two selector bugs the first draft of this block hit, both worth remembering for a future round that scripts a group chat check: (1) the group chat message row's testID (`group-chat-message-${id}`) shares its `group-chat-message-` prefix with every nested element inside it (`-body-`, `-pending-`, `-menu-`, `-media-`) — a prefix-matching locator's `.last()` resolves to whichever nested element happens to render last in the DOM (the body text), not the outer row that actually carries the timestamp sibling; the fix reads the exact testID of the mocked response's own id instead of a prefix match. (2) the timestamp `Text` is swapped for a pending-clock icon while the optimistic bubble is still in flight (`DocsGroupChatScreen.tsx`), so a check needs to wait for `group-chat-message-pending-*` to detach before reading the row — otherwise it reads the pending icon's absence of a timestamp as a 24-hour-format failure that was really just a timing race, not a format bug.

**Atomicity: two layers, not one.** `book_class` opens with `select ... for update` on the target `class_sessions` row before counting current bookings — two members' concurrent `book_class` calls for the same session genuinely serialize on that row lock in Postgres, so whichever commits first sees the true count and the second sees it already incremented; there is no window where both can read "1 spot left" and both insert. That's the hard guarantee, and it was proven directly against a real local Postgres instance (see "Database testing" below), not just reasoned about. The **second** layer is two partial unique indexes as a backstop that holds even if some future code path ever bypassed the row lock: `class_bookings_one_active_per_session_idx` (one `status = 'booked'` row per `(session_id, user_id)`, ever) and `class_bookings_one_first_class_free_ever_idx` (at most one `payment_method = 'first_class_free'` row per account, ever, regardless of status — the real enforcement for "first class free, once per account," which needed building from scratch: the brief's own premise of an "admin roster that tags first timers" doesn't exist anywhere in this codebase, so the partial index itself is both the write-time guarantee and the read-time "has this account used it" check, via `ClassBookingContext`'s own `sessions.some(s => getMyBooking(s.id)?.paymentMethod === 'first_class_free')`).

**Cancellation and refunds key off the booking's own recorded `payment_method`, not the member's current state.** This directly fixes a real, pre-existing latent bug in the old `useClassBooking.ts`: its `handleCancel` checked `membership.hasActivePack` *at cancel time*, which could wrongly refund a pack credit for a drop-in or first-class-free booking if the member happened to also hold an active pack by then. Because the brief's own data model requires recording `payment_method` per booking anyway, the correct fix (refund based on what THIS booking actually cost, immutably) falls out for free. `cancel_class_booking` returns `payment_method, needs_stripe_refund, stripe_checkout_session_id` — a pack-credit booking calls `refund_class_pack_credit()` (migration_019) internally; an `unlimited` booking is simply released; a drop-in/Pilates booking signals `needs_stripe_refund: true`, which `ClassBookingContext.cancel()` acts on immediately by calling a new Edge Function, `refund-booking` (same category as every other trusted Stripe call this app makes — a Postgres function can't call out to Stripe itself). That function takes only a `bookingId`, never a Stripe session id the client could hand in directly — it re-derives whose booking it is, what was actually paid, and whether it's really cancelled from the booking's own row via the service-role client (never trusting the RPC's own ownership check to have been the only gate, since this is a separate HTTP endpoint with its own service-role reach), then looks up the Checkout Session's PaymentIntent and calls `stripe.refunds.create()` with an idempotency key keyed to the booking id (a real backstop against a double-refund, not just an assumed one — the UI's own state already prevents a double cancel in practice, since a cancelled booking stops being returned as `myBooking`). A refund failure is logged, never surfaced as "your cancellation failed" — the booking is already genuinely cancelled by the time this runs, regardless of how the refund call itself goes.

**A real, caught-before-shipping gap: nothing told `ClassPackContext` its own credit count had changed server-side.** `book_class`/`cancel_class_booking` spend/refund a pack credit entirely inside the database transaction — but `ClassPackContext` (the context that actually drives the "X OF 10 CLASSES LEFT" number everywhere it's shown) only ever reads `class_packs` on mount or when something explicitly calls its own `refetch()`. Nothing in the booking flow did, which would have shipped a real bug: book or cancel a pack-credit class and the displayed credit count silently goes stale until some unrelated refetch happens to fire. Fixed in `useClassBooking.ts` — `classPack.refetch()` is called directly after a successful `pack_credit` booking and after cancelling a booking whose own recorded `payment_method` was `pack_credit`, mirroring the exact "optimistic local update, then reconcile with a refetch" convention `ClassPackContext.useCredit()`/`refundCredit()` already used for the OLD system's local-only spend/refund calls (those two methods are now dead code — nothing calls them anymore, since the server spends/refunds the credit itself — but were left in place rather than deleted, since `checkoutRedirect.ts` still calls `classPack.refetch()` directly on a 10 Class Pack *purchase*, a separate, still-live code path).

**Waitlist: join, auto-promote, and a second real gap — the promoted member's own app had no way to find out.** `join_waitlist(p_session_id, p_payment_method)` is only offered to `unlimited`/`pack_credit` members on a full capped class ("drop in and other pay-at-booking guests do not get waitlist in this version, they simply see CLASS FULL, since auto-charging a card on promotion is not acceptable" — Pilates, uncapped, never reaches this path at all). `cancel_class_booking` ends by checking for the earliest-joined `status = 'waiting'` entry on the same session and, if one exists, calls an internal-only helper, `_promote_waitlist_spend_pack_credit(target_user_id)` — **not** granted to `authenticated`/`anon` at all, reachable only via a function-to-function call from `cancel_class_booking` itself, needed because the standard `use_class_pack_credit()` is hard-scoped to `auth.uid()` and can't spend a credit on behalf of an arbitrary waitlisted user during an automatic promotion. The promoted member's own waitlist row flips to `promoted` and a real `booked` row is created for them, spending their own payment method at that moment — all server-side, triggered by someone else's cancellation. The gap: `ClassBookingContext` had no mechanism at all for a member's own screen to learn their waitlist entry had just become a real booking, short of them happening to trigger some other refetch. Fixed with a `supabase.channel(...).on('postgres_changes', ...)` subscription on `class_bookings`/`class_waitlist` (unfiltered, same convention as `GroupChatUnreadContext`'s own `group_chat_messages` channel — RLS already means this account is only ever sent rows it can read, so no ownership check is needed to stay correct, only to stay cheap) that calls `refetch()` on any change once the context has already loaded once. This is also the direct, real mechanism behind "sees it reflected in the app" for brief item 4, not an assumption.

**Capacity: per-template, cascading to every not-yet-happened session.** Doc's classes default to a cap of 30 ("planned bump to 50 around Memorial Day" reads as a global, not per-instance, change), editable via `admin_update_template_capacity(p_class_key, p_capacity)`, which updates both `class_templates.default_capacity` (so future-generated sessions inherit it) and every already-generated-but-not-yet-happened `class_sessions` row of that `class_key` in the same call — so a capacity bump is visible immediately, not just for sessions generated after the change. A third real gap, same shape as the pack-credit one above: `AdminRosterScreen.tsx`'s own `CapacityRow.save()` called the RPC and showed SAVED, but never refetched `ClassBookingContext`'s own `sessions` — admin_update_template_capacity touches `class_sessions`/`class_templates`, neither of which the new realtime channel above listens to (deliberately scoped to bookings/waitlist, not every table an admin action might touch), so the roster's own headcount badges kept showing the stale capacity number until something else refetched. Fixed by having `CapacityRow.save()` call the booking context's own `refetch()` directly after a successful save.

If the webhook's own `book_class` call fails (a genuine edge case the brief itself flagged: Stripe can't be synchronously capacity-checked at the moment Checkout is created in the browser, so a session could theoretically fill between checkout creation and webhook confirmation) or `classSessionId` is missing from the metadata, the webhook writes the failure onto `in_person_purchases.booking_error` instead of silently dropping it — a paid checkout with no booking is now visible in admin roster data rather than lost.

## Round 31: black Movement Vault videos (a YouTube embed flakiness bug, not an access gate), a stale popup surviving sign-out, and Search's own deck-card teaser never matched reality

Three real-device bugs plus an owner decision formalizing what Round 30's own gating had already made structurally true. No database changes.

**Part 1: Movement Vault videos rendering as a solid black box.** Reproduced directly with Playwright before touching any code, per the brief's own instruction not to assume: Movement Vault opened cold and warm, as both a limited-access and a full-access account, with the real `youtube-nocookie.com` embed request stubbed to succeed. Every one of those opens rendered the real player correctly, with exactly one embed request per open and no unexpected reload — confirming Round 29/30's own `closeAllOverlays`/`DeckCardDetailModal` gating changes have no connection to this bug at all. The real cause is the YouTube embed itself: `MovementVideoPlayer.tsx`'s old web branch was a one-shot `<iframe>` with no load handling whatsoever — if the embed request hangs (blocked, offline, slow network), the cross-origin iframe gives JS no signal of any kind, not even an error event, so `playerWrap`'s own black `backgroundColor` just stays visible forever behind nothing. This was confirmed directly: a route that never fulfills (simulating a genuinely hung request, the one failure shape that produces no `load` event at all) left the old code black indefinitely.

**The fix:** `WebVideoEmbed`, a new stateful component inside `MovementVideoPlayer.tsx`, races a 7-second timeout against the iframe's own `onLoad` — if `load` hasn't fired in time, it bumps a `key` (forcing React to tear down and mount a genuinely new iframe / browsing context, not a cached retry of the same one) and restarts the race, up to 2 automatic retries, before giving up and showing an actionable "Couldn't load video. Tap to retry." card instead of a silent black box forever. A second, independent layer covers the failure mode a timeout can't catch at all: the outer embed document can load fine (firing `load` immediately) while YouTube's own further-nested player never paints a frame — ordinary ad-blocker/slow-CDN flakiness with zero cross-origin signal to react to. A small always-visible reload button in the video's own corner (not just shown after a detected failure) gives the member a way to recover from exactly that case, matching "never leave a silent black box" for both the detectable and the undetectable failure shapes. Verified directly: a hung request auto-exhausts to the retry card after 3 total attempts (~21s), the retry card's own tap recovers the real player once the next request is allowed through, and the reload button is present even on an already-successful load. Owner decision, reaffirmed: this video has no tier check, overlay, or lock on it at all — `MovementVideoPlayer` takes no membership prop and never will.

**Part 2: the UNLOCK EVERYTHING nudge surviving sign-out onto the public welcome page.** Root-caused by reading the code: `AlertHost` (the shared renderer behind `showAlert()`, 25+ call sites) is mounted once in `App.tsx`, ABOVE the signed-in/signed-out branch — deliberately, so a confirmation dialog on a pre-signup screen like `PricingScreen` can still use it. Its own state (`alert.ts`'s `setStateRef`) and the shared interruption gate (`interruptionGate.ts`'s `owner`) are both plain module-level variables, entirely independent of auth state — nothing about the screen underneath switching from `MainApp` to the signed-out `OnboardingFlow` ever told either of them to clear. `TrialExpiryModal`/`TourOverlay`/`PurchaseCelebrationOverlay`, by contrast, are all rendered INSIDE `MainApp` itself, so they unmount cleanly the instant `signedUp` flips false — confirmed by reading their render positions directly; only the two module-level mechanisms needed a fix.

**The fix, two layers.** `alert.ts` gained `dismissAlert()` and `interruptionGate.ts` gained `releaseAllInterruptions()` (force-clears the slot regardless of current owner, unlike the existing `releaseInterruption(kind)` which only releases a slot the caller itself still holds) — `AuthContext.tsx`'s `signOut()` now calls both, synchronously, before even starting the real `supabase.auth.signOut()` call, so there's no race with how fast the auth listener happens to propagate. Second, structural layer in `App.tsx`: `AlertHost` itself is now gated `!(!signedUp && onboardingStep === 'about')` — NOT a blanket `signedUp` check, which would have broken `PricingScreen`/`OnlineStartScreen`/`InPersonPlansScreen`'s own real `showAlert()`-based checkout confirmations (all reachable before `signedUp` is ever true). Only the one screen the brief named — the public welcome/About page — is permanently incapable of rendering a popup, regardless of what `alert.ts` happens to be holding at the moment; every other pre-signup screen keeps working exactly as before. Verified end to end: a fresh online_free session shows the nudge, dismissing it normally and then running the real Settings → SIGN OUT → confirm flow lands cleanly on the welcome screen with zero popups.

**Part 3: Search's own deck-card "teaser" never matched a real device, and why Round 30's own check didn't catch it.** Round 30's PR described a limited-access account's search still surfacing a completed deck card as a tappable teaser row, locked on tap. A real device searching a deck card name as a limited account got no deck result at all — not a teaser, nothing. Root-caused directly: Round 30's own `[deck-gate/search-door]` check mocked a `deck_completions` row straight over the network to force a result into existence, bypassing the UI entirely. That shape can never occur on a real device: the ONLY way a completion is ever written is `DeckCardDetailModal`'s own MARK COMPLETE button, which the SAME Round 30 PR had already gated to `fullContentAccess` — so a limited-access account's real `deck_completions` is always empty in practice, `SearchModal.tsx`'s own `deckResults` (still filtered on `isComplete(c.id)` at the time) was always going to come up empty on a real device, and the check's own forced mock never actually exercised that real computation at all. The check technically ran and technically passed, but against a world that can't exist.

**Owner decision, formalizing what was already true in practice:** deck cards do not appear in search results for a limited-access tier at all, full stop — consistent with APPEARS IN being hidden for them since Round 30. `SearchModal.tsx`'s `deckResults` now checks `fullContentAccess` directly instead of relying on "nobody can ever have a completion" as the only enforcement — a member who completes cards on a full-access tier and later downgrades would otherwise keep seeing their old completions in search, which the "structural accident" alone would never catch. The old "visible teaser, locked on tap" behavior described in Round 30 is gone; `DeckCardDetailModal`'s own `locked` prop (App.tsx) is untouched and stays in place as defense-in-depth, in case any future door ever reaches it.

`scripts/verify-standalone-safe-area.js`'s `[deck-gate/search-door]` block was rewritten, not just extended, to match: a limited-access account gets NO deck result for "uni" even with a `deck_completions` row still mocked (proving the explicit access check, not an absence of fixture data, is what's doing the work), and a separate full-access check confirms the same completed card still appears and still opens the real content — unaffected. New `[movement-video/*]` checks (both tiers) assert the real player renders with the correct embed src and never falls back to the retry card, plus that the always-available reload control is present even on success.
